# 02 — Product requirements document

## 1. Product definition

LearnNova helps a student turn a supplied curriculum and available time into an actionable study plan, then adjusts remaining work from progress and limited assessment evidence.

Primary user: a student preparing selected curriculum objectives before a deadline. Secondary stakeholder: an educator or judge inspecting relevance, logical sequencing and feasibility. Curriculum maintenance is developer-managed for the prototype; no educator portal is required.

Value proposition: fits recorded availability, respects foundations, explains choices, and remembers what actually happened.

## 2. Success and limits

Prototype success means the full journey works on reviewed fixtures, no invalid schedule is activated, evidence persists, and outputs are relevant under a human rubric. Immediate independent follow-up performance can be shown. Long-term retention and causal learning gains are not established by the demo.

Performance targets are design targets until benchmarked: ordinary local reads under 300 ms; planning without generation under 2 seconds for 12 topics/30 days; generation acceptance returns a job ID promptly; initial full enrichment target under 30 seconds on the chosen warm model. Record actual hardware, model and cold/warm results. Missing these targets triggers optimization or honest reporting, not invented metrics.

## 3. User stories and acceptance

| ID | Story | Required behavior |
|---|---|---|
| P01 | I select what I need to learn | Published curriculum and explicit target selection; prerequisites included |
| P02 | I describe my deadline and availability | Inclusive date horizon, editable dated capacities, zero-capacity days allowed |
| P03 | I optionally state confidence | Stored as self-report, never displayed as assessed mastery |
| P04 | I request a plan | Saved job, visible status, dated sessions with topic/time/activity |
| P05 | I understand why | Reasons reference recorded goals, capacity, prerequisites or evidence |
| P06 | My goal may not fit | Explicit shortfall/deferred work; no silent omission or date extension |
| P07 | I complete or miss work | Idempotent event recorded; completed work protected |
| P08 | I check understanding | Reviewed question, server scoring, hints distinguished from independence |
| P09 | My situation changes | New revision; old plan marked stale; explicit update request |
| P10 | I return later | Saved profile, attempts and plan history remain |
| P11 | I export the result | CSV/JSON download reflects a specific saved plan version |

## 4. Input policy

Student inputs are normal application fields. Internal requests are JSON generated by the application. No student file upload or data-format knowledge is necessary.

Required: curriculum, one or more target topics, start date, deadline, at least one date with positive capacity. Optional: short goal text and per-target confidence. A zero-capacity profile can be saved for honesty, but generation returns a no-capacity plan outcome without fabricated sessions.

Dates use the student's recorded IANA timezone, default Asia/Kolkata. Audit timestamps are UTC. Start/deadline are local calendar dates; deadline is inclusive. No exact-time calendar integration in MVP.

Goal text helps retrieval but does not silently change target topics. If an explicit target is missing, generation is blocked with an actionable validation error.

The demonstration uses one current goal per student. If multiple saved goals exist, their feasibility is evaluated independently using separately allocated budgets; this prototype does not reconcile a shared calendar across concurrent goals. Do not claim that independent plans jointly fit a student's day.

## 5. Plan semantics

Every plan version has a goal ID, input revision, algorithm/config version, feasibility, ordered entries, deferred work, generation status and metrics. The active version can be stale when later evidence exists; it remains readable until replaced.

Sessions are atomic work units. Missing a session leaves it unfinished. Completing it once reduces remaining work once. Actual minutes are recorded separately from estimated minutes. Partial task completion is deferred: the MVP does not infer remaining instructional coverage from elapsed minutes.

Selected topic scope is never reduced without a visible partial-plan label and deferred list. Students may explicitly change targets. Foundational work supporting retained topics cannot be omitted merely to display greater coverage.

## 6. Adaptation policy

The system supports three triggers: progress, assessment, and changed availability/goal. Each updates student input_revision. Replanning is explicit in MVP; the application may offer it immediately, but does not launch a new job after every answer.

Rules use assessment evidence with an evidence-count guard; supported attempts do not equal independent success. No evidence means unknown. Self-report changes starting priority but cannot exempt required work by itself.

Strong evidence may reduce practice by a bounded amount. Weak evidence may insert focused practice; dependent tasks move only when necessary. All completed work remains in history. Adjustments are provisional planning decisions, not clinical/psychological labels.

## 7. Infeasibility behavior

FULL: every mandatory unfinished work unit fits with ordering constraints.

PARTIAL: some work fits, and every omitted unit is listed with reason; the application says the complete goal does not currently fit.

NO_CAPACITY: no useful minimum activity can be placed; empty schedule, explicit unresolved work and choices.

A positive minute shortfall is a lower bound on additional effort required. When precedence/fragmentation prevents placement despite enough total minutes, use a placement-conflict explanation, not a false zero-shortfall success.

## 8. Nonfunctional requirements

- Local restart persistence and repeatable developer seed.
- Separate public question payloads from answer keys.
- No model request while a database write transaction is held.
- Idempotent mutating requests and stale-input conflict handling.
- Plain explanations generated from evidence-backed reason codes.
- Bounded model requests, transparent fallback origin, no arbitrary tool execution.
- Traceability from requirements to acceptance checks.
- Backend independent of frontend choice.

## 9. Delivery cut line

First complete M0 and M1. If behind schedule, remove fancy charts, semantic goal matching and alternate explanations before removing plan validity, saving progress or grounded activities. At least one live model-generated activity path must work to establish R07; a fallback-only demo does not satisfy the intended GenAI delivery.
